## Open issues

### ID: ISSUE-001
- **Title:** Hero garment renders as a black box if the VideoGarment stacking rule is violated
- **Severity:** HIGH (visual regression of the primary hero)
- **Status:** MITIGATED (rule documented; no code guard)
- **Description:** Adding `z-index` or `opacity` to the `VideoGarment` media layer creates a nested stacking context; the alpha-composited garment then paints as an opaque black box. — CONFIRMED (source doc comment + debugging history).
- **Reproduction:** Add `z-10` or `opacity-*` to the `<video>`/`<img>` in `VideoGarment.tsx` while the hero is in `GARMENT_MODE="video"`.
- **Root cause:** Nested stacking context breaks the blend group / normal compositing established by the hero section's `isolate`. — CONFIRMED.
- **Fix:** Keep the layer `position: relative` with **no** z-index/opacity; rely on `isolate` on the parent `<section>`. — CONFIRMED.
- **Regression test:** None automated; visual check. See FAILURES.md F-001.

### ID: ISSUE-009
- **Title:** Order prices and status are client-chosen — a customer can insert `status:'paid', total:1`
- **Severity:** **CRITICAL** (blocks any real payment; financial-integrity failure)
- **Status:** RESOLVED (Phase 1, 2026-10-19) — order creation moved to `create-order` Edge Function (service role, DB-backed catalogue, JWT verification, retries). Client-supplied amounts rejected; prices recomputed server-side. Verified via API test.
- **Description:** `createOrder` (`src/lib/orders.ts`) sends client-computed `subtotal`, `shipping_cost`, `total`, `items`, `address`, `payment_method` **and `status`**; the `public.orders` insert policy constrains only `auth.uid() = user_id`, and a column default does not override an explicitly supplied value. Any authenticated customer can therefore write an arbitrary amount or a paid-looking order. There is **no server-side recomputation anywhere**. — CONFIRMED (`supabase/migrations/20261018_orders.sql`, `src/lib/orders.ts`, `src/pages/Checkout.tsx`).
- **Reproduction:** Sign in, then `supabase.from("orders").insert({ …, total: 1, status: "paid" })` with a valid `order_number` — the row is accepted.
- **Root cause:** Price authority lives in the browser; the only server-side control is RLS row ownership, not value integrity.
- **Fix:** a Supabase Edge Function (service role) that recomputes prices from its own catalogue and sets `status`. **Do NOT revoke the insert grant first** — orders would stop being creatable.
- **Regression test:** None. Needs an integration test against a real project once the function exists.

### ID: ISSUE-010
- **Title:** Midtrans provider stub trusts the client-computed `amount` and `items[].price`
- **Severity:** HIGH (latent — unreachable today)
- **Status:** RESOLVED (Phase 1, 2026-10-19) — `create-payment` Edge Function mints Snap token server-side from the order row; frontend invokes via `VITE_PAYMENT_ENDPOINT`. Webhook verifies signature + amount + idempotency. End-to-end tested: order → payment → webhook → status `paid`.
- **Description:** `midtransProvider.pay` POSTs `{order_id, amount: order.total, items:[{name, price, quantity}]}` to `VITE_PAYMENT_ENDPOINT` straight from the client order object. The provider is registered but hard-coded `available: false` (`// Wave 1`), so it cannot run today. — CONFIRMED (`src/lib/payments.ts`).
- **Root cause:** The endpoint contract was sketched client-first; nothing forced the server to be authoritative.
- **Fix:** the endpoint must ignore the request body and recompute from its own catalogue keyed on `order_id`.
